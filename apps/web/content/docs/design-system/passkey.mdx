## Try it

Passkeys need a secure context: `localhost` works as-is, any other host needs HTTPS (see [testing on phones](#testing-on-phones-and-other-devices)). Opening the preview in a new tab is the most reliable way to run the browser prompts.

### Demo script

<Steps>
<Step>
### Create
Enter a name and email and select **Create a passkey**; approve with Face ID / Touch ID / PIN. The card shows what the server stored: a public key and metadata — and explicitly no private key.

<Step>
### Come back
Reload the preview (↻ in the toolbar). It greets you by name and offers **Sign in with passkey**. No username or password.
</Step>
<Step>
### Cross-device: synced vs. device-bound
Open the same URL on another device signed into the same Apple or Google account (or 1Password) and choose **Sign in with an existing passkey**. It works without registering again and the card shows **Passkey type: Synced**. Repeat with a YubiKey to see **Device-bound**.
</Step>
<Step>
### Phone as authenticator
On a desktop that doesn't have the passkey, sign in and pick "Use a phone or tablet" in the browser prompt to scan the QR code.
</Step>
<Step>
### Reset demo
The link at the bottom wipes the mock store and asks the password manager to hide the old passkeys (Signal API, where supported).
</Step>
</Steps>

<Callout title="No device handy?">
Chrome DevTools → **More tools → WebAuthn** → *Enable virtual authenticator environment* → add an authenticator (`ctap2`, `internal`, resident keys and user verification **on**). The whole flow then runs without a phone or biometric.
</Callout>

## Testing on phones and other devices

Use a tunnel and open the HTTPS URL on every device:

```bash
ngrok http 3000
```

The mock derives the RP ID and origin from the request, so no configuration is needed. Passkeys are bound to the domain: ones created on `localhost` won't appear on the ngrok URL, so create them on the URL you'll demo from. For a fixed domain set `RP_ID`, `RP_ORIGIN` and `RP_NAME` in `.env.local`.

## The contract

Four endpoints, relative to `NEXT_PUBLIC_PASSKEY_API_BASE` (default `/api/auth/passkey`), all using the standard WebAuthn Level 3 JSON shapes so any server library fits behind them (SimpleWebAuthn, Yubico java-webauthn-server, Fido2NetLib, go-webauthn, py_webauthn). The *options* call sets an httpOnly challenge cookie that the matching *verify* call consumes — so the BED must either sit on the same origin (proxy it through this route) or allow credentialed CORS from the app.

| Endpoint | Body | Returns |
| --- | --- | --- |
| `POST /register/options` | `{ name, email }` | `PublicKeyCredentialCreationOptionsJSON` |
| `POST /register/verify` | `RegistrationResponseJSON` | `{ user, credential }` |
| `POST /login/options` | `{}` | `PublicKeyCredentialRequestOptionsJSON` |
| `POST /login/verify` | `AuthenticationResponseJSON` | `{ user, credential }` |

`session` and `reset` exist only on the mock.

## Your passkeys: the list, with readable names

A site cannot read the passkeys stored on a device or in a password manager; browsers block that to prevent tracking. What it can list is the relying party's own records for the signed-in customer, which is what every account page does. WebAuthn returns no name for a passkey, so the RP builds one:

| Source | Produces | Where it is computed |
| --- | --- | --- |
| AAGUID → authenticator model | "iCloud Keychain", "1Password", "Windows Hello", "YubiKey 5 NFC" | `mock-server/label.ts` `authenticatorNameFor()` against the vendored community list `aaguids.json`. "Not disclosed" for an all-zero AAGUID. |
| Request context at registration | "Safari on iPhone", "Chrome on Windows", plus the date | `platformLabelFor(request)` from the user agent, at `register/verify`. This is the code that moves into the Next.js proxy route when the BED takes over storage. |
| User nickname | "Work laptop" | `PATCH /passkeys/:id` |

Display rule: nickname if set, otherwise `<authenticator> · <platform> · added <date>`, otherwise `Passkey · added <date>`. After you sign in, the panel shows the list with Rename and Revoke. Revoke calls the Signal API so the password manager hides the revoked passkey where supported.

Register from two devices through ngrok (a laptop and a phone) to get a list that reads "Apple Passwords · Safari on iPhone · added 16 Sep 2026" and "Google Password Manager · Chrome on macOS · added 16 Sep 2026".

<Callout type="info" title="What the BED must return">
`aaguid`, `transports`, `backedUp`, `createdAt`, `lastUsedAt`, `authenticatorName`, `platformLabel`, `nickname`, and the derived `name`; plus `GET /passkeys`, `PATCH /passkeys/:id` and `DELETE /passkeys/:id` returning the remaining IDs. The contract in `features/auth/passkey/contract.ts` has the exact types.
</Callout>

## Detecting a passkey and prompting to sign in

The site cannot ask whether a passkey exists. It can invite the browser to use one in ways that stay silent when there is none. The demo below runs the three layers in order and prints which one did what:

1. **Immediate mediation.** `navigator.credentials.get({ mediation: "immediate" })` shows the passkey sheet at once if this browser holds one for the RP ID, and rejects instantly with no UI if not. Feature detected with `getClientCapabilities().immediateGet`; not every browser has it yet.
2. **Conditional UI.** A pending request is armed so the email field (`autocomplete="username webauthn"`) offers passkeys in its autofill bar. The broadest support, including iPhone and iPad.
3. **Relying party hint.** The mock sets a `passkey-hint` cookie when a platform passkey was created or used from this browser; on return the panel shows "Sign in with your passkey" as the primary action. An inference, but it works everywhere.

Whatever the layer, a phone can act as the authenticator for a desktop through the QR path, so "no passkey on this device" is never a dead end.

### How to test the layers

| Step | What to expect |
| --- | --- |
| Open the preview on a device with no passkey for this RP ID | The capabilities card shows what the browser supports; the trace ends with "no passkey" and the form is shown. |
| Create a passkey with Face ID / Touch ID, then reload the preview | The hint is set: "Sign in with your passkey" becomes the primary button. On a browser with immediate mediation the sheet appears on its own; otherwise tap the email field to see the passkey in the autofill bar. |
| Chrome DevTools virtual authenticator (`internal`, resident key + UV on) | Conditional UI works; immediate mediation depends on the Chrome version, and the trace says which. |
| Reset demo | Clears the hint and the store; the next load behaves as a new device. |

<Callout type="warn" title="One WebAuthn request at a time">
The browser allows a single pending WebAuthn request per tab, and that limit covers every preview iframe on this page. If the nudge preview armed its conditional UI request on load, the Create passkey button in the first preview would fail with "A request is already pending". So the nudge preview waits until you click or tap inside it (its trace shows "waiting" until then), and the client cancels its own pending request before starting any ceremony. If you still see the pending message, another preview on the page holds the request: reload the page and use one preview at a time.
</Callout>

## Controlling the "Choose where to save your passkey" sheet

That sheet is driven entirely by the **registration options the relying party sends** — the site controls it, not the SDK and not the device. The two settings that matter are `authenticatorSelection` (restricts *which kinds* of authenticator are offered) and `hints` (WebAuthn L3: *orders* the kinds without excluding any). Two things the site does **not** control: which password manager stores the passkey (iCloud Keychain vs Google vs 1Password is the user's OS setting), and the label in the sheet — that's the RP ID and `rp.name`, i.e. `RP_ID` / `RP_NAME` (in production the registrable domain, so one passkey works across `www.`, `shop.`, `id.`).

| Setting | Effect on the sheet |
| --- | --- |
| `authenticatorAttachment: "platform"` | Only the device keychain (Face ID / Touch ID / Windows Hello). Hides security keys and "use another device". |
| `authenticatorAttachment: "cross-platform"` | Only external authenticators: security keys, a phone via QR. |
| omitted (`any`) | Everything offered — the long list. |
| `hints: ["client-device"]` etc. | Leads with that kind but keeps the rest available. Safer than attachment when you want a default, not a restriction. Ignored by older browsers. |
| `residentKey: "required"` | Discoverable passkey — what enables sign-in without a username. Keep. |
| `userVerification: "required"` | Biometric / PIN mandatory. Keep for banking. |
| `excludeCredentials` | Prevents a second passkey on an authenticator that already holds one. Set automatically. |

| Preset | On an iPhone / iPad (Safari) | On a Mac / Windows laptop (Chrome) | Chrome DevTools virtual authenticator |
| --- | --- | --- | --- |
| **Consumer default** (`any` + hint `client-device`) | Sheet leads with iCloud Keychain; "Other options" reveals security key / other device. | Google Password Manager or iCloud Keychain first; "Use a different device" and security key below. | Works with a `ctap2` / `internal` authenticator; also with `usb`. |

| **Security key only** (`cross-platform`) | Only NFC/USB security keys and "other device"; the device keychain is hidden. | Only security key / phone via QR. | Only a `usb` / `nfc` / `ble` authenticator works. |
| **Everything, no preference** (`any`, no hints) | Full list, platform order. | Full list, platform order. | Any authenticator. |

To reproduce a real domain label instead of "localhost", run through ngrok (`RP_ID`/`RP_NAME` derived from the request) or set them in `.env.local`. Remember passkeys are bound to the RP ID: switch `attachment` freely, but changing `RP_ID` starts from an empty list.

## Policy choices baked in

- **User verification required** (biometric or PIN) for both ceremonies — banking-grade; `USER_VERIFICATION` in `mock-server/server.ts`.
- **Discoverable credentials required** — what makes "Sign in with passkey" work without typing an email.
- **Attestation: none.** Privacy-preserving authenticators (Apple) report an all-zero AAGUID, shown as "Not disclosed".
- The WebAuthn user handle is random bytes, never the email.

## Next: plugging into the OTP flow

Not built yet, by design. The pieces are in place: `useAuth().meetsRequirement({ acr, evidence })` already models passkey as `acr: 2` / `evidence: ["passkey"]`, so a `GuardedLink` for a high-assurance destination would request that and the auth overlay would offer **Sign in with passkey** before falling back to the OTP steps. After sign-in the BED creates the session and hands off to the assurance engine; the frontend only redirects.
